# Dinoco v2.1.7

This page tracks what changed release over release. Each entry links to the page that documents the feature in depth — treat this as a changelog, not the primary reference.

## v2.1.7

- **fix(postgres): typed parent keys in relation CTE (text = bigint on includes).** On PostgreSQL, `includes` failed with `operator does not exist: text = bigint` whenever the relation key was not text, for example snowflake `BIGINT` ids: `find_many::<FeeGroup>().includes(|x| x.fees().includes(|x| x.parts()))`. Since 2.1.0, an include sends the parent keys in a `VALUES` list, and PostgreSQL types a parameter there as `text`, so comparing it with the `bigint` column failed. Each key is now cast to the type of the value it holds (`$1::bigint`, `$1::text`, the native enum type, ...). This covers has-many, belongs-to and nested includes, with and without `take`/`skip`. Many-to-many includes and relation counts were not affected: they compare their parameters with a column directly. SQLite and MySQL send the same SQL as before, and query hooks and the logger now show the casts too. See [Includes](/en-us/docs/orm/orm/includes).

## v2.1.6

- **A freshly migrated PostgreSQL or MySQL database no longer reports drift.** Dinoco read string, enum and negative number defaults back wrong: PostgreSQL reports them with a cast (`'USER'::"Role"`, `'anon'::text`, `'-3'::integer`) and MySQL 8 without quotes (`USER`), and both were taken as no default. Any `@default("...")`, enum `@default(VALUE)` or negative `@default(-1)` made `migrate generate` fail right after applying the migration with `The migration finished, but the live database still does not match the Dinoco schema`, even on an empty database. They are now read as the schema declares them. Schema snapshots that `migrate run` recorded before 2.1.6 lack those defaults, so they are taken from the live columns when such a snapshot is read.
- **Table and column names that are SQL keywords work everywhere.** Only 15 keywords were quoted, so a model `User` (table `user`) failed on PostgreSQL with `syntax error at or near "user"`, and names such as `key`, `desc`, `end`, `range`, `rank`, `values`, `to` or `system` failed on MySQL. Every keyword PostgreSQL, MySQL 8.4 or SQLite reserves is now quoted, in migrations and in every query, including relation includes and relation counts, which wrote table names unquoted. SQLite schema inspection no longer fails on such a table either. See [Model attributes](/en-us/docs/orm/guide/models#model-attributes).
- **Apply one workspace's schema to another.** With more than one workspace, `migrate generate` asks which workspace to apply the migrations to, then which schema to apply: `dinoco/schema.dinoco` or the copy saved for another workspace. `--schema-from dev` answers without a terminal, and `models generate` accepts it too. The picked schema becomes the target workspace's saved copy. See [Apply another workspace's schema](/en-us/docs/orm/guide/configuration#apply-another-workspace-s-schema).
- **Rows that can't take a change stop the command before anything is written.** A column made required while rows hold `NULL` in it, or a required column without a default added to a table with rows, is reported with its table and row count, instead of failing halfway through the migration (MySQL commits each DDL statement on its own). See [Dangerous changes](/en-us/docs/orm/tooling/migrations#dangerous-changes).
- **Table, column and enum names longer than the database keeps are rejected.** PostgreSQL silently cut them to 63 bytes, so the database never matched the schema, and MySQL refused them over 64 characters halfway through a migration. `migrate generate` now lists them before connecting. See [Long index names](/en-us/docs/orm/guide/indexes#long-index-names).
- Upgrading: no migration is needed. A database where 2.1.5 applied the migration and then failed has the migration recorded without its schema snapshot: run `dinoco migrate generate` once more and approve adopting the history (`--adopt-baseline` without a terminal). Queries now quote reserved names, which changes the SQL text only for those names.

## v2.1.5

- **Long generated names match the database.** PostgreSQL keeps at most 63 bytes of an identifier and cut longer index names on its own, so a name such as `idx_business_receivable_transaction_business_id_executed_at_unlock_at` was stored as `..._unl` while Dinoco expected the full name, and every `dinoco migrate` reported `Missing index` and `Unexpected index` for it. MySQL refused those names outright. Generated index, unique, full-text and foreign key names, and the names of implicit many-to-many pivot tables and their columns, are now cut to the database's limit (63 bytes on PostgreSQL, 64 characters on MySQL) the same way PostgreSQL does, with a `_2`, `_3`, ... suffix when two names of a table would become equal. SQLite names don't change. See [Long index names](/en-us/docs/orm/guide/indexes#long-index-names).
- Upgrading: no migration is needed. The cut names are the ones PostgreSQL already stored, and the schema snapshots recorded by earlier versions are cut the same way when they are read.

## v2.1.4

- **PostgreSQL connects over TLS.** The PostgreSQL adapters always connected in plaintext, whatever the URL said, so servers that only accept TLS, such as Neon, refused them with `no TLS implementation configured`. They now follow the URL's `sslmode` with libpq's meaning: `disable` stays in plaintext, the default `prefer` uses TLS when the server supports it, `require` insists on it, and `verify-ca` and `verify-full` also check the server certificate against Mozilla's roots, which are compiled into the binary. The CLI follows the same setting. See [PostgreSQL TLS](/en-us/docs/orm/orm/clients-adapters#postgresql-tls).
- Upgrading: a server with TLS enabled now gets an encrypted connection without any change to the URL. Add `sslmode=disable` to keep the previous plaintext behavior. `sslmode=verify-ca` and `sslmode=verify-full`, rejected as an invalid URL before, are now accepted.

## v2.1.3

- **`count` and `exists` run inside transactions.** `count::<M>()` and `exists::<M>()` now accept the `tx` of a `transaction` or `transaction_with_error` closure, so `.execute(tx)` works on every builder. They run on the transaction's connection and see the rows the closure wrote before them, committed or not, and the relation counts requested with `.includes(...)` run there too. Before, both took `&client` only and saw committed rows only. They also accept the other executors `find_many` does, such as an `Arc` of the client. See [Read inside a transaction](/en-us/docs/orm/orm/transactions#read-inside-a-transaction) and [Count inside a transaction](/en-us/docs/orm/orm/count#count-inside-a-transaction).
- `count::<M>()` without relation counts no longer copies its filters, which saves one allocation per call on every database.
- `CountLoader::load_count`, which generated code calls for relation counts, receives the connection to read from (`&ReadSource`) instead of `&DinocoClient`. Only a hand-written `CountLoader` implementation needs to change.

## v2.1.2

- **`exists_complex` and `not_exists_complex` on relation fields.** They are `exists()` and `not_exists()` narrowed to the related rows that match a [where complex](/en-us/docs/orm/orm/where-complex) tree, checked against one related row: `t.payout.exists_complex(|payout, m| m.or(payout.method.eq(PayoutMethod::Ted), payout.method.eq(PayoutMethod::Boleto)))` keeps the transactions with a Ted or Boleto payout. They compile to the same SQL as `where_complex` and `none_complex`. See [Filter methods](/en-us/docs/orm/orm/relation-filters#filter-methods).

## v2.1.1

- **`none_complex` and `every_complex` on relation fields.** They are `none` and `every` with a [where complex](/en-us/docs/orm/orm/where-complex) tree over the related row, the way `where_complex` extends `where_`. The whole tree is checked against one related row: `t.items.none_complex(|item, m| m.and([item.refunded.eq(true), item.note.null()]))` keeps the transactions without an item that is both refunded and missing a note. Before, this took `WhereComplex.and(...)` inside `none`, or `m.not(...)` in the builder's own `where_complex`, which also drops every plain `where_` on that builder. See [Filter methods](/en-us/docs/orm/orm/relation-filters#filter-methods).

## v2.1.0

> [!WARNING]
> Three changes can need action when upgrading, each described below: Rust 1.95 is now the minimum version, `u64`, `usize`, `u128`, and `i128` convert into `DinocoValue` with `TryFrom` instead of `From`, and `dinoco migrate generate` no longer reads answers from a pipe.

- **The CLI explains what it is about to do.** Every command that touches a database starts with a **Target** section (workspace, database, location with credentials hidden, migrations directory), and `migrate generate` shows the **Migration Plan** with `+`/`~`/`-` markers and a count by kind, the **Data Impact** of destructive changes, and the **Actions** approval will run, listing writing the files and applying them as separate steps. In a terminal, the approval prompt can show the migration SQL first, and it starts on **Cancel** when the plan is destructive. All output is in English. Results go to standard output, while warnings, errors, and progress go to standard error. Colors are used only on terminals and follow `NO_COLOR`, `--no-color`, and `CLICOLOR_FORCE`. See [Output, colors, and errors](/en-us/docs/orm/tooling/cli#output-colors-and-errors).
- **Errors say what to do next.** Each error names what failed, the facts it failed on, why when that is known, and the next step. Connection URLs are always printed with the `user:password@` part and password-like query parameters hidden, including inside driver messages.
- **Non-interactive mode and exit codes.** Without a terminal, with `--non-interactive`, or with `CI` set, the CLI never waits for input. Every decision has an option, and a missing one stops the command with exit code `2` and names the option to pass. Exit codes are `0` (success), `1` (failure), `2` (invalid usage or a decision required), and `130` (cancelled). See [Exit codes](/en-us/docs/orm/tooling/cli#exit-codes).
- Upgrading scripts: an answer piped into `migrate generate` (`echo y | dinoco migrate generate`) is no longer read. Pass `--yes`, or `--allow-destructive` for plans with destructive changes. The `DINOCO_CLI_CONFIRM_MIGRATION`, `DINOCO_CLI_CONFIRM_DESTRUCTIVE`, and `DINOCO_CLI_CONFIRM_DRIFT` variables keep working as before. See [Environment variables from earlier releases](/en-us/docs/orm/tooling/cli#environment-variables-from-earlier-releases).
- **Renames are confirmed, never assumed.** Each rename the planner infers is asked about: keep the data with a rename, or plan a removal plus an addition. Without a terminal, pass `--rename user.username=display_name`, `--no-rename ...`, or `--accept-renames`. A confirmed rename is no longer reported as a destructive change. See [Renames](/en-us/docs/orm/tooling/migrations#renames).
- **Replacements for removed enum values.** When an enum value is removed while rows still use it, `migrate generate` shows how many rows use it and asks which existing value replaces it (`--replace-enum-value Status.Processing=Pending` without a terminal). The migration rewrites those rows before the column stops accepting the old value. This covers MySQL and SQLite; PostgreSQL still refuses enum value removal. See [Removed enum values](/en-us/docs/orm/tooling/migrations#removed-enum-values).
- **`migrate generate --create-only`** writes `up.sql` and `down.sql` without applying them or regenerating the models, for review before `dinoco migrate run`. See [Create a migration without applying it](/en-us/docs/orm/tooling/migrations#create-a-migration-without-applying-it).
- **`dinoco init --database ... --connection ...`** answers the setup questions on the command line.
- **Workspaces are never chosen for you.** A schema with a single workspace uses it, and the Target section shows it. With several workspaces, the CLI asks, listing where each one's database URL comes from, or, without a terminal, asks for `--workspace`.
- **Checked integer conversions.** `DinocoValue` stores integers as `i64`. `From<u64>`, `From<usize>`, `From<u128>`, and `From<i128>` used to wrap or truncate values outside that range without a sign. They are replaced by `TryFrom`, which returns `IntegerOutOfRange`. Upgrading: use `DinocoValue::try_from(value)?`, or convert to `i64` yourself where the value is known to fit. Smaller integer types still use `From`. See [Value types](/en-us/docs/orm/reference/api-reference#value-types).
- **Less work per query.** Every adapter compiles SQL in a single pass into one buffer: compiling a find with five conditions now allocates 2 times instead of 106 to 152, and a 100-row PostgreSQL insert 2 times instead of 2,125. Rows are decoded by column position, results stream into their models, and inserts move values instead of cloning them.
- **Cargo features per database.** `dinoco` has `sqlite`, `postgres`, `mysql`, and `cli` features, all enabled by default. A SQLite-only build compiles 48 crates instead of 213. See [Cargo features](/en-us/docs/orm/orm/clients-adapters#cargo-features).
- **MySQL keeps prepared statements across pooled connections.** Connections are no longer reset when they return to the pool, which saves a round trip per query. Add `?reset_connection=true` to the URL if raw SQL changes session variables. See [MySQL](/en-us/docs/orm/guide/configuration#mysql).
- **Rust 1.95 or newer is required**, for the updated drivers: `rusqlite` 0.40, `deadpool-sqlite` 0.14, `mysql_async` 0.37, and `deadpool-postgres` 0.14.
- The VS Code extension's language server moved from `tower-lsp`, which is no longer maintained, to `tower-lsp-server`. Its features are unchanged.
- Fixed: on MySQL, `migrate generate` failed after applying a schema that uses enums, reporting a missing enum type that MySQL never creates.
- Fixed: on MySQL, migrations failed for database names longer than 46 characters, because the migration lock name exceeded MySQL's 64-character limit.
