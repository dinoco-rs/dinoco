# Dinoco v2.1.7

Esta página acompanha o que mudou release a release. Cada item linka para a página que documenta a funcionalidade em profundidade — trate isto como um changelog, não como a referência principal.

## v2.1.7

- **fix(postgres): typed parent keys in relation CTE (text = bigint on includes).** No PostgreSQL, os `includes` falhavam com `operator does not exist: text = bigint` sempre que a chave da relação não era texto, por exemplo ids snowflake `BIGINT`: `find_many::<FeeGroup>().includes(|x| x.fees().includes(|x| x.parts()))`. Desde a 2.1.0, um include envia as chaves dos pais numa lista `VALUES`, e o PostgreSQL tipa um parâmetro ali como `text`, então a comparação com a coluna `bigint` falhava. Agora cada chave recebe um cast para o tipo do valor que guarda (`$1::bigint`, `$1::text`, o tipo enum nativo, ...). Isso cobre includes has-many, belongs-to e aninhados, com e sem `take`/`skip`. Includes many-to-many e contagens de relações não eram afetados: eles comparam os parâmetros direto com uma coluna. SQLite e MySQL enviam o mesmo SQL de antes, e os hooks de query e o logger agora também mostram os casts. Veja [Includes](/pt-br/docs/orm/orm/includes).

## v2.1.6

- **Um banco PostgreSQL ou MySQL recém-migrado não reporta mais drift.** O Dinoco lia errado os defaults de string, enum e números negativos: o PostgreSQL os mostra com um cast (`'USER'::"Role"`, `'anon'::text`, `'-3'::integer`) e o MySQL 8 sem aspas (`USER`), e os dois eram tratados como sem default. Qualquer `@default("...")`, `@default(VALOR)` de enum ou `@default(-1)` negativo fazia o `migrate generate` falhar logo depois de aplicar a migration com `The migration finished, but the live database still does not match the Dinoco schema`, mesmo num banco vazio. Agora eles são lidos como o schema declara. Os snapshots de schema gravados pelo `migrate run` antes da 2.1.6 não têm esses defaults, então eles são lidos das colunas do banco quando um snapshot assim é carregado.
- **Nomes de tabela e coluna que são palavras-chave do SQL funcionam em todo lugar.** Só 15 palavras-chave eram colocadas entre aspas, então um model `User` (tabela `user`) falhava no PostgreSQL com `syntax error at or near "user"`, e nomes como `key`, `desc`, `end`, `range`, `rank`, `values`, `to` ou `system` falhavam no MySQL. Toda palavra-chave que o PostgreSQL, o MySQL 8.4 ou o SQLite reserva agora vai entre aspas, nas migrations e em toda query, incluindo includes e contagens de relações, que escreviam nomes de tabela sem aspas. A inspeção de schema do SQLite também não falha mais numa tabela assim. Veja [Atributos do model](/pt-br/docs/orm/guide/models#atributos-do-model).
- **Aplique o schema de um workspace em outro.** Com mais de um workspace, o `migrate generate` pergunta em qual workspace aplicar as migrations e depois qual schema aplicar: o `dinoco/schema.dinoco` ou a cópia salva para outro workspace. `--schema-from dev` responde sem terminal, e o `models generate` também aceita a opção. O schema escolhido vira a cópia salva do workspace de destino. Veja [Aplicar o schema de outro workspace](/pt-br/docs/orm/guide/configuration#aplicar-o-schema-de-outro-workspace).
- **Rows que não aceitam uma mudança param o comando antes de qualquer escrita.** Uma coluna que vira obrigatória enquanto rows guardam `NULL` nela, ou uma coluna obrigatória sem default adicionada a uma tabela com rows, é reportada com a tabela e o número de rows, em vez de falhar no meio da migration (o MySQL confirma cada comando DDL sozinho). Veja [Alterações perigosas](/pt-br/docs/orm/tooling/migrations#alteracoes-perigosas).
- **Nomes de tabela, coluna e enum maiores que o banco guarda são recusados.** O PostgreSQL os cortava em 63 bytes sem avisar, e o banco nunca batia com o schema, e o MySQL os recusava acima de 64 caracteres no meio de uma migration. O `migrate generate` agora os lista antes de conectar. Veja [Nomes de índice longos](/pt-br/docs/orm/guide/indexes#nomes-de-indice-longos).
- Ao atualizar: nenhuma migration é necessária. Um banco em que a 2.1.5 aplicou a migration e depois falhou tem a migration registrada sem o snapshot de schema: rode `dinoco migrate generate` mais uma vez e aprove a adoção do histórico (`--adopt-baseline` sem terminal). As queries agora colocam nomes reservados entre aspas, o que muda o texto do SQL só para esses nomes.

## v2.1.5

- **Nomes gerados longos batem com o banco.** O PostgreSQL guarda no máximo 63 bytes de um identificador e cortava por conta própria os nomes de índice maiores, então um nome como `idx_business_receivable_transaction_business_id_executed_at_unlock_at` era gravado como `..._unl` enquanto o Dinoco esperava o nome completo, e todo `dinoco migrate` reportava `Missing index` e `Unexpected index` para ele. O MySQL recusava esses nomes de vez. Os nomes gerados de índice, unique, full-text e foreign key, e os nomes das tabelas pivô implícitas de many-to-many e de suas colunas, agora são cortados no limite do banco (63 bytes no PostgreSQL, 64 caracteres no MySQL) do mesmo jeito que o PostgreSQL faz, com um sufixo `_2`, `_3`, ... quando dois nomes de uma tabela ficariam iguais. Os nomes no SQLite não mudam. Veja [Nomes de índice longos](/pt-br/docs/orm/guide/indexes#nomes-de-indice-longos).
- Ao atualizar: nenhuma migration é necessária. Os nomes cortados são os que o PostgreSQL já tinha gravado, e os snapshots de schema gravados por versões anteriores são cortados do mesmo jeito quando são lidos.

## v2.1.4

- **O PostgreSQL conecta via TLS.** Os adapters PostgreSQL sempre conectavam sem criptografia, independentemente do que a URL dizia, então servidores que só aceitam TLS, como o Neon, recusavam a conexão com `no TLS implementation configured`. Agora eles seguem o `sslmode` da URL com o significado do libpq: `disable` continua sem TLS, o padrão `prefer` usa TLS quando o servidor suporta, `require` exige TLS, e `verify-ca` e `verify-full` também verificam o certificado do servidor contra as raízes da Mozilla, compiladas no binário. A CLI segue a mesma configuração. Veja [TLS no PostgreSQL](/pt-br/docs/orm/orm/clients-adapters#tls-no-postgresql).
- Ao atualizar: um servidor com TLS habilitado passa a receber uma conexão criptografada sem nenhuma mudança na URL. Adicione `sslmode=disable` para manter o comportamento anterior, sem TLS. `sslmode=verify-ca` e `sslmode=verify-full`, que antes eram rejeitados como URL inválida, agora são aceitos.

## v2.1.3

- **`count` e `exists` rodam dentro de transactions.** `count::<M>()` e `exists::<M>()` agora aceitam o `tx` de uma closure de `transaction` ou `transaction_with_error`, então o `.execute(tx)` funciona em todo builder. Eles rodam na conexão da transaction e enxergam as rows que a closure escreveu antes deles, commitadas ou não, e os counts de relação pedidos com `.includes(...)` também rodam ali. Antes, os dois aceitavam apenas `&client` e só enxergavam rows commitadas. Eles também aceitam os outros executores que o `find_many` aceita, como um `Arc` do client. Veja [Leia dentro de uma transaction](/pt-br/docs/orm/orm/transactions#leia-dentro-de-uma-transaction) e [Conte dentro de uma transaction](/pt-br/docs/orm/orm/count#conte-dentro-de-uma-transaction).
- `count::<M>()` sem counts de relação não copia mais seus filtros, o que economiza uma alocação por chamada em todo banco.
- `CountLoader::load_count`, que o código gerado chama para os counts de relação, recebe a conexão de onde ler (`&ReadSource`) no lugar de `&DinocoClient`. Só uma implementação de `CountLoader` escrita à mão precisa mudar.

## v2.1.2

- **`exists_complex` e `not_exists_complex` nos fields de relação.** São o `exists()` e o `not_exists()` restritos às rows relacionadas que batem com uma árvore de [where complex](/pt-br/docs/orm/orm/where-complex), avaliada sobre uma mesma row relacionada: `t.payout.exists_complex(|payout, m| m.or(payout.method.eq(PayoutMethod::Ted), payout.method.eq(PayoutMethod::Boleto)))` mantém as transactions com um payout Ted ou Boleto. Eles geram o mesmo SQL que o `where_complex` e o `none_complex`. Veja [Methods de filtro](/pt-br/docs/orm/orm/relation-filters#methods-de-filtro).

## v2.1.1

- **`none_complex` e `every_complex` nos fields de relação.** São o `none` e o `every` com uma árvore de [where complex](/pt-br/docs/orm/orm/where-complex) sobre a row relacionada, do mesmo jeito que o `where_complex` estende o `where_`. A árvore inteira é avaliada sobre uma mesma row relacionada: `t.items.none_complex(|item, m| m.and([item.refunded.eq(true), item.note.null()]))` mantém as transactions sem nenhum item que esteja, ao mesmo tempo, estornado e sem nota. Antes isso exigia `WhereComplex.and(...)` dentro do `none`, ou `m.not(...)` no `where_complex` do próprio builder, que também descarta todo `where_` comum desse builder. Veja [Methods de filtro](/pt-br/docs/orm/orm/relation-filters#methods-de-filtro).

## v2.1.0

> [!WARNING]
> Três mudanças podem exigir ação ao atualizar, cada uma descrita abaixo: Rust 1.95 passa a ser a versão mínima, `u64`, `usize`, `u128` e `i128` convertem para `DinocoValue` com `TryFrom` em vez de `From`, e o `dinoco migrate generate` não lê mais respostas de um pipe.

- **A CLI explica o que vai fazer.** Todo comando que toca um banco começa com uma seção **Target** (workspace, banco, localização com credenciais ocultas, diretório de migrations), e o `migrate generate` mostra o **Migration Plan** com marcadores `+`/`~`/`-` e uma contagem por tipo, o **Data Impact** das mudanças destrutivas e as **Actions** que a aprovação vai executar, com escrever os arquivos e aplicá-los como passos separados. Num terminal, a pergunta de aprovação pode mostrar o SQL da migration antes, e começa em **Cancel** quando o plano é destrutivo. Toda a saída é em inglês. Os resultados vão para a saída padrão, e avisos, erros e progresso para a saída de erro. Cores só aparecem em terminais e seguem `NO_COLOR`, `--no-color` e `CLICOLOR_FORCE`. Veja [Saída, cores e erros](/pt-br/docs/orm/tooling/cli#saida-cores-e-erros).
- **Os erros dizem o que fazer a seguir.** Cada erro diz o que falhou, os fatos sobre o que falhou, o motivo quando ele é conhecido e o próximo passo. URLs de conexão são sempre impressas com a parte `usuario:senha@` e os parâmetros de query com cara de senha ocultos, inclusive dentro das mensagens do driver.
- **Modo não interativo e exit codes.** Sem terminal, com `--non-interactive` ou com `CI` definido, a CLI nunca espera por entrada. Toda decisão tem uma opção, e a falta de uma para o comando com exit code `2` e diz qual opção passar. Os exit codes são `0` (sucesso), `1` (falha), `2` (uso inválido ou decisão necessária) e `130` (cancelado). Veja [Exit codes](/pt-br/docs/orm/tooling/cli#exit-codes).
- Atualizando scripts: uma resposta enviada por pipe ao `migrate generate` (`echo y | dinoco migrate generate`) não é mais lida. Passe `--yes`, ou `--allow-destructive` para planos com mudanças destrutivas. As variáveis `DINOCO_CLI_CONFIRM_MIGRATION`, `DINOCO_CLI_CONFIRM_DESTRUCTIVE` e `DINOCO_CLI_CONFIRM_DRIFT` continuam funcionando como antes. Veja [Variáveis de ambiente de releases anteriores](/pt-br/docs/orm/tooling/cli#variaveis-de-ambiente-de-releases-anteriores).
- **Renames são confirmados, nunca presumidos.** Cada rename que o planner infere é perguntado: manter os dados com um rename, ou planejar uma remoção mais uma adição. Sem terminal, passe `--rename user.username=display_name`, `--no-rename ...` ou `--accept-renames`. Um rename confirmado não é mais apontado como mudança destrutiva. Veja [Renames](/pt-br/docs/orm/tooling/migrations#renames).
- **Substitutos para valores de enum removidos.** Quando um valor de enum é removido enquanto linhas ainda o usam, o `migrate generate` mostra quantas linhas o usam e pergunta qual valor existente o substitui (`--replace-enum-value Status.Processing=Pending` sem terminal). A migration reescreve essas linhas antes que a coluna deixe de aceitar o valor antigo. Vale para MySQL e SQLite; o PostgreSQL continua recusando a remoção de valores de enum. Veja [Valores de enum removidos](/pt-br/docs/orm/tooling/migrations#valores-de-enum-removidos).
- **`migrate generate --create-only`** escreve `up.sql` e `down.sql` sem aplicá-los nem regenerar os models, para revisão antes do `dinoco migrate run`. Veja [Crie uma migration sem aplicá-la](/pt-br/docs/orm/tooling/migrations#crie-uma-migration-sem-aplica-la).
- **`dinoco init --database ... --connection ...`** responde às perguntas de setup pela linha de comando.
- **Workspaces nunca são escolhidos por você.** Um schema com um único workspace usa esse workspace, e a seção Target o mostra. Com vários, a CLI pergunta, listando de onde vem a URL do banco de cada um, ou, sem terminal, pede `--workspace`.
- **Conversões de inteiros verificadas.** O `DinocoValue` guarda inteiros como `i64`. `From<u64>`, `From<usize>`, `From<u128>` e `From<i128>` truncavam valores fora dessa faixa sem aviso. Eles foram trocados por `TryFrom`, que retorna `IntegerOutOfRange`. Para atualizar: use `DinocoValue::try_from(value)?`, ou converta para `i64` você mesmo onde o valor certamente cabe. Tipos inteiros menores continuam usando `From`. Veja [Tipos de valor](/pt-br/docs/orm/reference/api-reference#tipos-de-valor).
- **Menos trabalho por query.** Todos os adapters compilam o SQL numa única passada, num único buffer: compilar um find com cinco condições agora faz 2 alocações em vez de 106 a 152, e um insert de 100 linhas no PostgreSQL faz 2 em vez de 2.125. As linhas são decodificadas pela posição da coluna, os resultados vão direto para os models, e os inserts movem os valores em vez de cloná-los.
- **Features do Cargo por banco.** O `dinoco` tem as features `sqlite`, `postgres`, `mysql` e `cli`, todas habilitadas por padrão. Um build só com SQLite compila 48 crates em vez de 213. Veja [Features do Cargo](/pt-br/docs/orm/orm/clients-adapters#features-do-cargo).
- **O MySQL mantém prepared statements entre conexões do pool.** As conexões não são mais resetadas ao voltar para o pool, o que economiza uma ida e volta por query. Adicione `?reset_connection=true` à URL se SQL cru muda variáveis de sessão. Veja [MySQL](/pt-br/docs/orm/guide/configuration#mysql).
- **Rust 1.95 ou mais novo é exigido**, pelos drivers atualizados: `rusqlite` 0.40, `deadpool-sqlite` 0.14, `mysql_async` 0.37 e `deadpool-postgres` 0.14.
- O language server da extensão do VS Code trocou o `tower-lsp`, que não é mais mantido, pelo `tower-lsp-server`. As funcionalidades não mudaram.
- Corrigido: no MySQL, o `migrate generate` falhava depois de aplicar um schema com enums, apontando um tipo enum ausente que o MySQL nunca cria.
- Corrigido: no MySQL, as migrations falhavam para nomes de banco com mais de 46 caracteres, porque o nome do lock de migration passava do limite de 64 caracteres do MySQL.
