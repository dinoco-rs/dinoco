# Testing

Dinoco ships a test ambient: a real database for your tests that needs no server, no Docker, and no cleanup. `create_test_ambient()` opens a fresh in-memory SQLite database, creates every table, index, and foreign key declared in `dinoco/schema.dinoco`, and hands back an ordinary `DinocoClient`. `setup_test_methods::<M>(&client)` then lets a test watch every insert, update, delete, and find that touches model `M`, so a route test can check what the route did to the database, not only what it answered.

```rust
use dinoco::{create_test_ambient, remove_test_methods, setup_test_methods};

let client = create_test_ambient().await?;

setup_test_methods::<User>(&client)
    .on_insert(|inserted, query, error| { /* ... */ })
    .on_update(|affected, query, error| { /* ... */ })
    .on_delete(|affected, query, error| { /* ... */ })
    .on_find(|rows, query, error| { /* ... */ });

// ... call the route or the function under test ...

remove_test_methods::<User>(&client);
```

## Create a test ambient

```rust
use dinoco::{create_test_ambient, find_first, insert_into};

#[tokio::test]
async fn creates_a_user() -> anyhow::Result<()> {
    let client = create_test_ambient().await?;

    insert_into::<User>().values(&user).execute(&client).await?;

    let stored = find_first::<User>()
        .where_(|x| x.email.eq("ana@example.com"))
        .execute(&client)
        .await?;
    assert!(stored.is_some());

    Ok(())
}
```

`create_test_ambient()` returns `anyhow::Result<DinocoClient>`, the same type `connect()` returns, so code that takes `&DinocoClient`, `Arc<DinocoClient>`, or an application state wrapping it works unchanged. Every builder works against it: `find_first`, `find_many`, `.includes(...)`, `count`, `exists`, `find_batch`, every insert/update/delete builder, and `transaction(...)`.

### What gets created

The tables are planned from the schema by the same engine behind `dinoco migrate generate`, then compiled for SQLite:

| In the schema | In the test database |
| --- | --- |
| `model` | A table with the model's table name |
| Scalar fields, `?` | Columns, `NOT NULL` unless optional |
| `@id`, `@@ids([...])` | Primary key, single or composite |
| `@default(...)` | Column default (`now()`, `autoincrement()`, enum values, literals); `uuid()`/`snowflake()` are generated by Dinoco on insert, as in production |
| `@unique`, `@@uniques([...])` | Unique indexes, so a duplicate fails with `CreateError::UniqueViolation` |
| `@index`, `@@indexes([...])` | Plain indexes |
| `@relation(...)` | Foreign keys, enforced (SQLite runs with `foreign_keys = ON`) |
| Implicit many-to-many | The pivot table |
| `enum` | A text column holding the variant's schema spelling |

**It is always SQLite, whatever `config.database` says.** A PostgreSQL or MySQL project gets the same tables, constraints, and indexes, so tests exercise the same rules the production database enforces.

### Isolation and parallel tests

Each call to `create_test_ambient()` gets its own empty database. `cargo test` runs tests in parallel threads, and none of them sees another's rows, so tests need no cleanup and no ordering:

```rust
#[tokio::test]
async fn first() -> anyhow::Result<()> {
    let client = create_test_ambient().await?; // empty
    // ...
    Ok(())
}

#[tokio::test]
async fn second() -> anyhow::Result<()> {
    let client = create_test_ambient().await?; // also empty, even while `first` runs
    // ...
    Ok(())
}
```

Inside one ambient, the database is shared by every pooled connection and every transaction of that client, just like a file-backed database: reads that run concurrently (`tokio::join!`, `.includes(...)`) and writes made in a committed transaction all see the same data. The database is freed when the client is dropped (with an `Arc<DinocoClient>`, when the last `Arc` is).

> [!TIP]
> Create one ambient per test. Building one is fast (the schema is compiled and the tables created in memory), and a fresh database keeps every test independent. Sharing one ambient between tests through a static brings back ordering problems that the ambient exists to remove.

### Options

`create_test_ambient()` reads `dinoco/schema.dinoco` relative to the current directory. Under `cargo test` that is the root of the crate being tested, which is where `dinoco init` puts the schema. `TestAmbient` covers the other cases:

```rust
use dinoco::TestAmbient;

// A schema somewhere else. The file must still be named `schema.dinoco`.
let client = TestAmbient::new()
    .schema(concat!(env!("CARGO_MANIFEST_DIR"), "/../app/dinoco/schema.dinoco"))
    .create()
    .await?;

// A schema that uses `config.workspace`: pick the workspace whose settings apply.
let client = TestAmbient::new().workspace("dev").create().await?;
```

| Method | Default | Effect |
| --- | --- | --- |
| `TestAmbient::new()` | — | Same as `create_test_ambient()` until you change something |
| `.schema(path)` | `dinoco/schema.dinoco` | Schema file to build the database from. Files it imports are resolved relative to it |
| `.workspace(name)` | none | Applies that workspace's configuration. An unknown name is an error |
| `.create().await` | — | Builds the database and returns the client |

From the configuration (after the workspace is applied), `with_logger` and `query_mode` are honored, so a schema with `with_logger = true` prints every SQL statement in tests too. `database`, `database_url`, `connection`, pool sizes, and `read_replicas` are ignored: the ambient never opens a network connection and needs no environment variables.

## The generated connect() in tests

The `dinoco/mod.rs` that code generation writes has three connection functions:

```rust
/// Connects to the database configured in `schema.dinoco`. When this crate is
/// compiled for its own tests (`cfg(test)`), it returns [`connect_test`]
/// instead, so code under test never reaches the real database.
pub async fn connect() -> ::dinoco::anyhow::Result<::dinoco::DinocoClient> {
    if cfg!(test) {
        return connect_test().await;
    }

    connect_database().await
}

/// A fresh in-memory SQLite database with every table of `schema.dinoco`,
/// isolated from every other call. See `dinoco::create_test_ambient`.
pub async fn connect_test() -> ::dinoco::anyhow::Result<::dinoco::DinocoClient> {
    ::dinoco::TestAmbient::new()
        .schema(concat!(env!("CARGO_MANIFEST_DIR"), "/dinoco/schema.dinoco"))
        .create()
        .await
}

/// Connects to the configured database, even under `cfg(test)`.
pub async fn connect_database() -> ::dinoco::anyhow::Result<::dinoco::DinocoClient> {
    let database_url = std::env::var("DATABASE_URL")?;
    // ... the adapter, replicas, logger, and query mode from `config` ...
}
```

| Function | Returns |
| --- | --- |
| `connect()` | `connect_test()` when the crate is compiled with `cfg(test)`, `connect_database()` otherwise |
| `connect_test()` | A new test ambient built from the crate's `dinoco/schema.dinoco` |
| `connect_database()` | The real database, as `connect()` did before 2.0.4 |

So code that calls `connect()` needs no change to be tested. `main` keeps connecting to the real database, and the same call inside `#[cfg(test)]` tests gets an isolated in-memory database, with no `DATABASE_URL` needed:

```rust
// src/main.rs
#[path = "../dinoco/mod.rs"]
mod database;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let client = database::connect().await?; // the real database
    // ...
    Ok(())
}

#[cfg(test)]
mod tests {
    use super::database;

    #[tokio::test]
    async fn each_call_is_isolated() -> anyhow::Result<()> {
        let first = database::connect().await?;  // test ambient
        let second = database::connect().await?; // another, empty test ambient

        dinoco::insert_into::<Project>().value(&Project::new("A".to_string())).execute(&first).await?;
        assert!(dinoco::find_many::<Project>().execute(&second).await?.is_empty());

        Ok(())
    }
}
```

When the schema uses `config.workspace`, `connect_test()` applies the workspace the models were generated for (`.workspace("dev")`), the same one `connect_database()` connects to.

Things to know about `cfg(test)`:

- It is set only while Rust compiles **this crate's own tests**: `#[cfg(test)]` modules and `#[test]` functions inside `src/`. Integration tests in `tests/`, benches, and other crates that depend on yours compile it without `cfg(test)`, so there `connect()` connects to the real database. From those, call `connect_test()` directly (for example through a `pub` function of your library crate), or `dinoco::create_test_ambient()`.
- `connect_test()` finds the schema through `CARGO_MANIFEST_DIR`, the directory of the crate's `Cargo.toml`. That is where `dinoco init` puts `dinoco/`. If your schema lives elsewhere (for example at a Cargo workspace root while the crate is a member), build the client with `TestAmbient::new().schema(...)` instead.
- Need the real database from a unit test (say, a test tagged `#[ignore]` that you run against a staging database)? Call `connect_database()`.

## Test a route

Route tests build the application state the same way `main` does, through the generated `connect()`. For an Axum app whose router takes `Arc<DinocoClient>`, a route test sends a request with `tower::ServiceExt::oneshot` and reads the response:

```toml
# Cargo.toml
[dev-dependencies]
http-body-util = "0.1"
serde_json = "1"
tower = { version = "0.5", features = ["util"] }
```

```rust
use std::sync::{Arc, Mutex};

use axum::{Router, body::Body, http::{Method, Request, StatusCode}};
use dinoco::setup_test_methods;
use http_body_util::BodyExt;
use serde_json::{Value, json};
use tower::ServiceExt;

async fn app() -> anyhow::Result<(Router, Arc<dinoco::DinocoClient>)> {
    // The same `connect()` as `main`: under `cfg(test)` it is the test ambient.
    let client = Arc::new(database::connect().await?);
    Ok((routes::router(client.clone()), client))
}

async fn send(app: &Router, method: Method, uri: &str, body: Option<Value>) -> anyhow::Result<(StatusCode, Value)> {
    let request = Request::builder()
        .method(method)
        .uri(uri)
        .header("content-type", "application/json")
        .body(body.map_or_else(Body::empty, |body| Body::from(body.to_string())))?;
    let response = app.clone().oneshot(request).await?;
    let status = response.status();
    let bytes = response.into_body().collect().await?.to_bytes();
    let body = if bytes.is_empty() { Value::Null } else { serde_json::from_slice(&bytes)? };

    Ok((status, body))
}

#[tokio::test]
async fn create_project_inserts_the_project_and_its_tasks_in_one_transaction() -> anyhow::Result<()> {
    let (app, client) = app().await?;
    let inserts = Arc::new(Mutex::new(Vec::new()));

    let log = inserts.clone();
    setup_test_methods::<Project>(&client).on_insert(move |rows, query, _| {
        log.lock().unwrap().push((query.table, rows.map(<[_]>::len), query.in_transaction));
    });
    let log = inserts.clone();
    setup_test_methods::<Task>(&client).on_insert(move |rows, query, _| {
        log.lock().unwrap().push((query.table, rows.map(<[_]>::len), query.in_transaction));
    });

    let (status, body) = send(
        &app,
        Method::POST,
        "/projects",
        Some(json!({ "name": "Launch", "tasks": ["Write docs", "Ship"] })),
    )
    .await?;

    assert_eq!(status, StatusCode::CREATED);
    assert_eq!(body["tasks"].as_array().map(Vec::len), Some(2));
    assert_eq!(
        *inserts.lock().unwrap(),
        [("project", Some(1), true), ("task", Some(1), true), ("task", Some(1), true)],
    );

    Ok(())
}
```

The last assertion checks something the response alone can't prove: the route inserted exactly one project and two tasks, all inside a transaction. The complete version of this suite is in `examples/axum/src/tests.rs` in the Dinoco repository. The same approach works with Actix Web (`actix_web::test::init_service`) or a plain Tower service. Outside `cfg(test)`, build the state from `connect_test()` or `create_test_ambient()` instead.

To seed data a route needs, use the builders directly on the same client before sending the request:

```rust
let project = insert_into::<Project>()
    .value(&Project::new("Existing".to_string()))
    .returning::<Project>()
    .execute(&*client)
    .await?;

let (status, _) = send(&app, Method::GET, &format!("/projects/{}", project.id), None).await?;
assert_eq!(status, StatusCode::OK);
```

## Observe queries per model

### Install callbacks

`setup_test_methods::<M>(&client)` returns a builder that installs callbacks for model `M` on that client. They run after every operation on `M`'s table:

- operations run on the client itself (`.execute(&client)`);
- operations run inside a `transaction(...)` opened on that client (`.execute(tx)`);
- `M` loaded as a relation through `.includes(...)` on another model;
- `M` rows inserted as a nested relation of another model's insert.

```rust
setup_test_methods::<User>(&client)
    .on_insert(|inserted, query, error| println!("insert into {}: {inserted:?} {error:?}", query.table))
    .on_update(|affected, query, _| println!("{} updated {affected:?} row(s)", query.table))
    .on_delete(|affected, query, _| println!("{} deleted {affected:?} row(s)", query.table))
    .on_find(|rows, query, _| println!("{} returned {rows:?} row(s)", query.sql));
```

Callbacks are scoped to the model: operations on `Post` never reach the callbacks of `User`. They are also scoped to the client: another `create_test_ambient()` in the same test doesn't see them.

Every method is optional; install only what the test needs. Calling `setup_test_methods::<M>` again for the same model keeps the callbacks already installed and adds the new ones. Setting a callback that already exists replaces it:

```rust
setup_test_methods::<User>(&client).on_insert(|_, _, _| println!("A"));
setup_test_methods::<User>(&client).on_find(|_, _, _| println!("B"));   // on_insert still prints "A"
setup_test_methods::<User>(&client).on_insert(|_, _, _| println!("C")); // replaces "A"
```

### Remove callbacks

`remove_test_methods::<M>(&client)` removes every callback of `M` from the client and leaves other models' callbacks in place. Calling it when nothing is installed does nothing.

```rust
setup_test_methods::<User>(&client).on_insert(|_, _, _| println!("user"));
setup_test_methods::<Post>(&client).on_insert(|_, _, _| println!("post"));

remove_test_methods::<User>(&client);
// inserting a User prints nothing; inserting a Post still prints "post"
```

Use it to observe only one step of a longer test, for example after seeding data and before calling the route:

```rust
seed_users(&client).await?;               // not observed

setup_test_methods::<User>(&client).on_update(/* ... */);
send(&app, Method::PATCH, "/users/1", Some(body)).await?; // observed
remove_test_methods::<User>(&client);

send(&app, Method::GET, "/users", None).await?; // not observed
```

With a fresh ambient per test, callbacks are dropped with the client at the end of the test, so removing them is only needed within a test.

### What each callback receives

Every callback gets three arguments: the result, the executed query, and the error. Exactly one of the result and the error is `Some`.

| Callback | Result (1st argument) | Runs after |
| --- | --- | --- |
| `on_insert` | `Option<&[serde_json::Value]>`: the inserted rows, one JSON object per row keyed by column name | every `INSERT` into `M`: `insert_into`, `insert_many`, with or without `.returning`/`.pluck`, and nested relation inserts |
| `on_update` | `Option<usize>`: rows changed | `update`, `update_many`, `find_and_update` |
| `on_delete` | `Option<usize>`: rows removed | `delete`, `delete_many` |
| `on_find` | `Option<usize>`: rows returned | `find_first`, `find_many`, and every relation query that loads `M` through `.includes(...)` |

`insert_many` calls `on_insert` once for the whole batch, with every row in the slice. The inserted rows contain the values Dinoco sent, including generated `uuid()`/`snowflake()` ids. Values the database fills in by itself (`autoincrement()`, `now()` defaults) aren't there.

A relation query returns one row for each parent that points at a related row: loading the author of two posts written by the same person reports 2 rows.

The second argument is an `ExecutedQuery`:

| Field | Type | Meaning |
| --- | --- | --- |
| `table` | `&'static str` | Table the statement targets |
| `sql` | `String` | The SQL Dinoco compiled for the statement (SQLite syntax on the ambient) |
| `params` | `Vec<DinocoValue>` | Bound parameters, in order |
| `in_transaction` | `bool` | `true` when the statement ran through a `transaction(...)` context |

The third argument is `Option<&DatabaseError>`:

| Method | Returns |
| --- | --- |
| `error.constraint()` | `Option<DatabaseConstraintError>`: `UniqueViolation`, `ForeignKeyViolation`, `NotNullViolation`, `CheckViolation` |
| `error.constraint_details()` | `&ConstraintDetails`: `table`, `constraint`, `columns` as the driver reported them |
| `error.original()` | The driver error (`rusqlite::Error` on the ambient) |

The callback only observes the failure. The builder still returns its own typed error to the caller (`CreateError`, `UpdateError`, `AtomicUpdateError`, …), so the route's error handling runs exactly as in production.

## Common patterns

### Assert that a route wrote exactly what it should

```rust
let inserted = Arc::new(Mutex::new(Vec::new()));
let log = inserted.clone();
setup_test_methods::<Order>(&client).on_insert(move |rows, _, _| {
    log.lock().unwrap().extend(rows.unwrap_or_default().iter().cloned());
});

send(&app, Method::POST, "/orders", Some(json!({ "sku": "A-1", "quantity": 2 }))).await?;

let inserted = inserted.lock().unwrap();
assert_eq!(inserted.len(), 1);
assert_eq!(inserted[0]["quantity"], 2);
```

### Assert that a route didn't touch the database

Validation should reject bad input before any query runs:

```rust
let touched = Arc::new(Mutex::new(false));
let flag = touched.clone();
setup_test_methods::<Project>(&client).on_insert(move |_, _, _| *flag.lock().unwrap() = true);

let (status, _) = send(&app, Method::POST, "/projects", Some(json!({ "name": "   " }))).await?;

assert_eq!(status, StatusCode::BAD_REQUEST);
assert!(!*touched.lock().unwrap());
```

### Catch N+1 queries

`.includes(...)` loads a relation for every parent in one query. Counting `on_find` calls on the related model catches code that loads it in a loop instead:

```rust
let queries = Arc::new(Mutex::new(0));
let counter = queries.clone();
setup_test_methods::<Task>(&client).on_find(move |_, _, _| *counter.lock().unwrap() += 1);

send(&app, Method::GET, "/projects", None).await?;

assert_eq!(*queries.lock().unwrap(), 1, "tasks must come from one include query");
```

### Check the error a route ran into

```rust
let conflicts = Arc::new(Mutex::new(Vec::new()));
let log = conflicts.clone();
setup_test_methods::<User>(&client).on_insert(move |_, _, error| {
    if let Some(error) = error {
        log.lock().unwrap().push((error.constraint(), error.constraint_details().columns.clone()));
    }
});

send(&app, Method::POST, "/users", Some(json!({ "email": "taken@example.com" }))).await?;
let (status, _) = send(&app, Method::POST, "/users", Some(json!({ "email": "taken@example.com" }))).await?;

assert_eq!(status, StatusCode::CONFLICT);
assert_eq!(
    *conflicts.lock().unwrap(),
    [(Some(DatabaseConstraintError::UniqueViolation), vec!["email".to_string()])],
);
```

### Check affected rows

```rust
let deleted = Arc::new(Mutex::new(Vec::new()));
let log = deleted.clone();
setup_test_methods::<Task>(&client).on_delete(move |affected, _, _| log.lock().unwrap().push(affected));

send(&app, Method::DELETE, &format!("/tasks/{id}"), None).await?; // 204
send(&app, Method::DELETE, &format!("/tasks/{id}"), None).await?; // 404

assert_eq!(*deleted.lock().unwrap(), [Some(1), Some(0)]);
```

### Keep the helpers in one place

A small recorder keeps route tests short when several models are observed:

```rust
#[derive(Clone, Default)]
struct Events(Arc<Mutex<Vec<String>>>);

impl Events {
    fn record<M: dinoco::DinocoEntity>(&self, client: &DinocoClient) {
        let (insert, update, delete) = (self.clone(), self.clone(), self.clone());
        setup_test_methods::<M>(client)
            .on_insert(move |rows, q, _| insert.push(format!("insert {} {:?}", q.table, rows.map(<[_]>::len))))
            .on_update(move |n, q, _| update.push(format!("update {} {n:?}", q.table)))
            .on_delete(move |n, q, _| delete.push(format!("delete {} {n:?}", q.table)));
    }

    fn push(&self, event: String) {
        self.0.lock().unwrap().push(event);
    }

    fn take(&self) -> Vec<String> {
        std::mem::take(&mut *self.0.lock().unwrap())
    }
}

let events = Events::default();
events.record::<Project>(&client);
events.record::<Task>(&client);

send(&app, Method::POST, "/projects", Some(json!({ "name": "Launch", "tasks": ["Ship"] }))).await?;
assert_eq!(events.take(), ["insert project Some(1)", "insert task Some(1)"]);
```

## Inside transactions

A `transaction(...)` opened on the client reports its operations to the same callbacks, with `query.in_transaction` set to `true`. A callback runs as soon as its statement finishes, not at commit, so it also runs for work that is later rolled back. To check that a failed route left nothing behind, query the database after the request instead of relying on the callbacks:

```rust
let (status, _) = send(&app, Method::POST, "/projects", Some(json!({ "name": "Launch", "tasks": [""] }))).await?;

assert_eq!(status, StatusCode::BAD_REQUEST);
assert_eq!(count::<Project>().execute(&*client).await?.total, 0);
```

## Writing callbacks

- Callbacks must be `Fn + Send + Sync + 'static`: collect into an `Arc<Mutex<_>>` (or an atomic counter) that the test keeps a clone of, as in the examples above.
- They run synchronously right after the statement, on the task that executed it. Keep them short and don't `.await` inside them (they aren't async).
- A panic inside a callback fails the test when the route runs on the test's own task (`oneshot`, direct calls). If the code under test spawns its own tasks, a panic there can be lost, so record values in the callback and assert after the request.
- Callbacks never change the outcome of the operation. They can't make a query fail or return different rows.

## Limits

- `count`, `exists`, and `find_batch` don't trigger `on_find`.
- The pivot table of an implicit many-to-many relation has no model, so its inserts and deletes (`connect`, `disconnect`) can't be observed. The endpoints' own operations can.
- The ambient builds the schema's final shape directly. It doesn't replay files in `dinoco/migrations/`, so anything written by hand in a migration (seed rows, triggers, extra SQL in a manual migration) isn't there. Insert what a test needs in the test itself.
- SQLite isn't your production database. Features specific to PostgreSQL or MySQL, such as their full-text ranking, collations, and exact type limits, behave the SQLite way. Keep a few tests against the real database for those.

## Troubleshooting

| Message | Cause |
| --- | --- |
| ``failed to compile `dinoco/schema.dinoco` for the test ambient`` | The schema isn't at that path relative to the current directory, or it has an error. Run `cargo test` from the crate that owns the schema, or pass `.schema(concat!(env!("CARGO_MANIFEST_DIR"), "/dinoco/schema.dinoco"))` |
| `The main schema file must be named schema.dinoco` | `.schema(path)` must point at a file named `schema.dinoco` |
| ``workspace `x` was not found`` | `.workspace(name)` names a workspace the schema's `config` doesn't declare |
| `transaction context used outside its transaction closure` | A `tx` handle escaped its `transaction(...)` closure. This isn't specific to the ambient |
